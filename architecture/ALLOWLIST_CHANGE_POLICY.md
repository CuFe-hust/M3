# ALLOWLIST_CHANGE_POLICY.md — 文件白名单变更政策

本文件约束 `architecture/allowed_python_files.txt` 的变更方式。

## 1. 白名单是架构控制文件

- `architecture/allowed_python_files.txt` 冻结**整个新架构最终批准的 Python 路径**；
- 它不是"当前已存在文件清单"——当前实现状态以
  `architecture/implementation_status.json` 为准；
- 白名单中列出但尚未创建的文件是**已批准的未来路径**，不代表已经实现，
  也不允许预先创建空壳。

## 2. 普通任务不得修改白名单

- 编码代理在**普通实施任务**中禁止修改 `architecture/allowed_python_files.txt`；
- 如果当前任务要求的文件不在白名单：
  1. 停止实现；
  2. 报告缺失路径；
  3. 等待用户创建独立的"架构变更任务"；
  4. 不得自行扩展白名单。

## 3. 架构变更任务的要求

架构变更任务必须满足：

- 由用户显式批准（任务文件允许修改列表包含白名单路径）；
- 白名单变更必须**独立 commit**，不与业务实现混在一起；
- 必须说明**旧职责为什么无法容纳新路径**（例如：新模块边界、新测试文件）；
- 禁止通过"先改白名单、再建文件"的方式在普通任务中绕过文件范围约束。

## 4. 禁止泛化兜底文件

除非用户明确批准，禁止在白名单中加入：

```text
utils.py
helpers.py
manager.py
compat.py
legacy.py
common.py
```

以及任何形式的兼容层/兜底文件。职责必须落在明确的模块路径上。

## 5. 测试文件路径

- 测试文件同样必须显式列入白名单（不使用 `tests/**/*.py` 宽泛 glob）；
- 新测试文件的批准方式与生产文件相同：随任务文件由用户批准后加入白名单。

## 6. 永久禁止

- `spacers_agent/**` 与 `eval/**` 永久禁止（本分支从零重建，无兼容层）；
- 旧包目录不得重新创建。
