# M3-RS 标准化评测系统 —— 测试说明

**适用人员：** 模型开发与评测操作者
**前置条件：** Python 3.10+ 可用，本仓库已克隆到本地

---

## 1. 系统工作原理和目录说明

### 1.1 工作原理

M3-RS 标准化评测系统采用"**不可变运行包为事实来源，Excel 为派生展示层**"的架构：

```text
固定协议与数据清单
  → 标准请求 JSONL（系统自动生成）
  → 独立命令行被测系统（用户实现，符合 JSONL 契约）
  → 标准预测 JSONL（被测系统输出）
  → 完整性与 Schema 校验（系统自动执行）
  → 四套数据集指标适配器（调用官方/补充评测脚本）
  → 设备与资源采集器（自动采集硬件与运行指标）
  → 不可变 run 目录（runs/<run_id>/，运行完成后永不覆盖）
  → 历史 CSV/JSONL（history/runs.csv、metrics_long.csv、coverage.csv）
  → 核心评测表与报告上下文（Excel 工作簿 + JSON 上下文）
```

每次运行先保存原始证据（请求、预测、输出日志、资源配置），再更新历史汇总。不得只把最终分数写进 Excel 而丢弃样本级结果。

```text
└── 评测表.xlsx                         # 核心评测工作簿（可从历史重建）
```

### 1.3 关键设计原则

- **运行包不可变：** 已完成运行（`runs/<run_id>/`）的内容永不原地修改。重跑产生新 `run_id`。
- **历史 CSV 是事实来源：** `runs.csv`、`metrics_long.csv` 和 `coverage.csv` 由评测脚本写入，是 `rebuild-table` 和 `prepare-report` 的唯一数据来源。
- **Excel 是派生展示层：** `评测表.xlsx` 由 `build_workbook.py` 从历史 CSV 重建，不应该手动编辑数值字段。
- **全量正式运行与冒烟/部分运行严格隔离：** `mode=full` 且 `status=complete` 且协议检查通过的运行才进入正式历史比较。冒烟运行保存但标记为 `eligible_for_history=false`。

## 3. server.yaml 逐字段填写方法及数据来源

真实评测时，将 `configs/server.example.yaml` 复制为 `configs/server.local.yaml`（已加入 `.gitignore`），按以下说明逐字段填写。

### 3.1 顶层字段

| 字段 | 说明 | 数据来源 |
|------|------|----------|
| `project_root` | 项目根目录的绝对路径 | 仓库克隆位置，如 `/srv/m3rs/project` |
| `protocol_path` | 协议文件路径 | 固定为 `protocols/official_full_v1.yaml`，通常不修改 |
| `metric_registry_path` | 指标注册表路径 | 指向 `registry/metrics.yaml`（含 194 项指标） |
| `output_root` | 运行包输出根目录 | 如 `/srv/m3rs/project/runs`，需有写权限 |
| `system_version` | 本次运行的系统版本标识 | 由操作者自定，如 `v2.1-20260805`，用于 run_id 和版本对比 |
| `model_name` | 模型名称 | 如 `M3RS-ViT-L-336px`，用于元数据记录和评测表 |
| `model_weights` | 模型权重文件或目录路径 | 服务器上的实际路径 |
| `training_data_version` | 训练数据版本标识 | 如 `v3-augmented`，用于区分不同训练数据配置 |
| `operator` | 操作者姓名或团队标识 | 如 `zhangsan`，用于元数据记录 |

### 3.2 system 字段

| 字段 | 说明 | 数据来源 |
|------|------|----------|
| `system.command` | 被测系统的命令行（参数数组） | 系统的启动命令，见第 4 节 JSONL 契约。示例：`["python", "-m", "system_adapter"]` |
| `system.working_directory` | 命令执行的工作目录 | 系统的绝对路径 |
| `system.timeout_seconds` | 命令超时时间（秒） | 根据模型推理速度估算，全量四数据集建议 86400（24 小时）以上 |
| `system.environment` | 环境变量（如 `CUDA_VISIBLE_DEVICES`、API Token） | 实际 GPU 编号和认证信息。**包含 Token 的字段会在日志中自动脱敏** |

### 3.3 datasets 字段（四个数据集各一套）

以 `levir_cc` 为例（`vrsbench`、`xlrs_bench`、`mme_rs` 结构类似）：

| 字段 | 说明 | 数据来源 |
|------|------|----------|
| `root` | 数据集根目录 | 官方数据集下载后的解压路径 |
| `asset_root` | 图像资源根目录 | 如果图像与标注分开放置，填图像根目录；否则同 `root` |
| `profile` | 数据集配置模式 | 正式评测填 `official`；夹具测试填 `fixture` |
| `official_scorer_command` | 官方评测脚本命令（参数数组） | 各数据集官方仓库中的评测脚本路径和参数。支持占位符 `{input_jsonl}`、`{output_jsonl}`、`{references_jsonl}`、`{predictions_jsonl}`、`{output_json}` |
| `official_scorer_working_directory` | 官方评测脚本工作目录 | 官方评测仓库根目录 |
| `official_scorer_timeout_seconds` | 官方评测脚本超时时间 | 建议 600 秒 |
| `official_scorer_expected_version` | 预期的官方评测脚本版本号 | 从官方仓库 README 或 setup.py 获取 |
| `official_scorer_expected_commit` | 预期的官方评测脚本 Git commit | `git rev-parse HEAD` 在官方仓库中执行 |

**注意：** 夹具模式（`profile: fixture`）下，`official_scorer_command` 等字段被替换为直接读取测试夹具的预计算分数文件 `official_scorer_output`，不需要真实 GPU。


## 4. 被测系统 JSONL 契约和示例

### 4.1 请求格式（评测系统 → 被测系统）

评测系统生成一个标准 JSONL 文件，每行一个请求对象。被测系统通过 `{input_jsonl}` 占位符接收文件路径。

标准请求行示例（VRSBench VQA 任务）：

```json
{
  "sample_id": "vrsbench:vqa:000001",
  "dataset": "vrsbench",
  "benchmark_version": "release-and-manifest-hash",
  "split": "test",
  "task": "vqa",
  "images": ["/absolute/read-only/path/image.tif"],
  "prompt": "Question text fixed by protocol",
  "choices": ["A. airport", "B. harbor"],
  "expected_output": "choice",
  "request_hash": "sha256"
}
```

字段说明：
- `sample_id`：全局唯一样本标识，格式 `{dataset}:{task}:{序号}`
- `dataset`：数据集名（`levir_cc` / `vrsbench` / `xlrs_bench` / `mme_rs`）
- `benchmark_version`：数据集发布版本和测试清单哈希
- `split`：数据集划分，正式评测始终为 `test`（或 XLRS-Bench 的 `public_test`）
- `task`：任务类型（如 `caption`、`vqa`、`grounding`、`color`、`count`、`position`）
- `images`：图像绝对路径数组。LEVIR-CC 含两张时相图像（A 和 B），其他数据集通常一张
- `prompt`：协议锁定的固定提示词文本
- `choices`：选择题选项数组（仅 VQA/MME 任务有值；Caption 和 Grounding 为 `null`）
- `expected_output`：期望输出类型（`choice` / `text` / `boxes`）
- `request_hash`：请求内容的 SHA-256 哈希，用于完整性校验

LEVIR-CC 请求包含两张按协议排序的时相图像（A 图像在前，B 图像在后）。Grounding 请求的 `expected_output` 为 `boxes`。Caption 请求不包含 `choices` 字段。

### 4.2 预测格式（被测系统 → 评测系统）

被测系统必须将预测结果写入 `{output_jsonl}` 路径，**每行一个 JSON 对象**，`sample_id` 必须与请求一一对应。

标准预测行示例（status=ok，VQA 选择）：

```json
{
  "sample_id": "vrsbench:vqa:000001",
  "status": "ok",
  "prediction": "B",
  "boxes": null,
  "raw_output": "B",
  "latency_ms": 842.5,
  "error_code": null,
  "error": null,
  "trace": null
}
```

标准预测行示例（status=ok，Caption）：

```json
{
  "sample_id": "levir_cc:caption:000001",
  "status": "ok",
  "prediction": "a building has been constructed",
  "boxes": null,
  "raw_output": "a building has been constructed",
  "latency_ms": 1234.5,
  "error_code": null,
  "error": null,
  "trace": null
}
```

标准预测行示例（status=ok，Grounding boxes）：

```json
{
  "sample_id": "vrsbench:grounding:000001",
  "status": "ok",
  "prediction": null,
  "boxes": [[10.5, 20.3, 100.0, 200.0]],
  "raw_output": "[[10.5, 20.3, 100.0, 200.0]]",
  "latency_ms": 567.8,
  "error_code": null,
  "error": null,
  "trace": null
}
```

### 4.3 错误处理规则（status=error）

当被测系统无法为一个样本产生有效预测时，必须输出 `status: "error"`：

```json
{
  "sample_id": "levir_cc:caption:000099",
  "status": "error",
  "prediction": null,
  "boxes": null,
  "raw_output": null,
  "latency_ms": null,
  "error_code": "timeout",
  "error": "inference timed out after 30 seconds",
  "trace": null
}
```

### 4.4 错误码说明

| error_code | 含义 | 使用场景 |
|------------|------|----------|
| `timeout` | 推理超时 | 单样本推理时间超过系统设置的超时阈值 |
| `inference_error` | 推理错误 | 模型前向传播失败（如 OOM、CUDA error） |
| `parse_error` | 解析错误 | 模型输出无法解析为期望格式 |
| `cancelled` | 被取消 | 推理被外部信号中断 |
| `unknown` | 未知错误 | 其他未分类的错误 |

### 4.5 关键规则

1. **一一对应：** 输出 JSONL 的行数必须与输入 JSONL 相同，`sample_id` 必须完整匹配。缺失、重复、未知 ID 均计入失败。
2. **status=ok 必须含有效预测：** caption/VQA 填 `prediction`（字符串），grounding 填 `boxes`（数组）。两者互斥。
3. **status=error 必须含 error_code 和 error：** `prediction` 和 `boxes` 必须为 `null`。
4. **可选字段：** `latency_ms`（单样本推理耗时，毫秒）、`raw_output`（模型原始输出字符串）、`trace`（调试信息，任意 JSON）。
5. **评测器不得静默删除失败记录。** 所有缺失/重复/畸形/超时/错误预测均计入失败样本数（`n_failures`）。

### 4.6 Schema 校验

请求格式应符合 `schemas/request.schema.json`，预测格式应符合 `schemas/prediction.schema.json`。评测系统会在预测文件读入后自动校验。校验失败的行计入失败并记录到 `failures.jsonl`。


## 5. 四套数据集目录、split 和训练隔离检查

### 5.1 LEVIR-CC

- **正式测试范围：** 官方 `test` 全量。
- **Split 保护：** `train` 和 `val` 允许参与模型训练，但**不得进入正式评测结果**。评测脚本仅读取 `test` 数据。
- **主任务：** 变化描述（Caption）和变化判别（Change/No-Change Discrimination）。
- **主指标（Caption）：** `levir.caption.all.bleu_4`、`levir.caption.all.meteor`、`levir.caption.all.rouge_l`、`levir.caption.all.cider_d`（及 all/change/no-change 切片）。
- **特殊说明：** no-change 切片的 CIDEr-D 为 N/A（无参考描述），不以 0 代替。
- **训练隔离检查：** `doctor` 命令会扫描数据集目录结构，确认 `test` split 不与 `train`/`val` 混合。若检测到 train/val 样本出现在测试清单中，发出告警。

### 5.2 VRSBench

- **正式测试范围：** 官方 `test` 全量。
- **Split 保护：** `train` 和 `val` 允许训练或微调，但**不得进入正式评测结果**。
- **覆盖任务：** Caption、HBB Grounding、VQA。若数据发布包含 OBB（Oriented Bounding Box），作为附录协议单列。
- **Caption 主指标：** `vrs.caption.bleu_4`、`vrs.caption.meteor`、`vrs.caption.rouge_l`、`vrs.caption.cider`。
- **Grounding 主指标：** `vrs.grounding.hbb.all.acc_0_5`（及 Unique/Non-Unique/All 的 Acc@0.5/Acc@0.7，若有）。
- **VQA 主指标：** `vrs.vqa.acc.all`（及十类问题准确率）。确定性标准化结果为主，LLM Judge 单列为辅助。
- **训练隔离检查：** 同 LEVIR-CC，`doctor` 检查 test 与 train/val 隔离。

### 5.3 XLRS-Bench

- **正式测试范围：** 官方公开测试数据全量。**不得参与训练。**
- **Split 保护：** 无训练划分——所有公开测试任务禁止用于训练。`doctor` 不做 split 隔离检查，但记录该数据集声明"不得训练"。
- **Full 与 Lite 隔离：** Full 和 Lite 分别注册协议和版本，**禁止合并为同一平均分**。Full 测评结果与 Lite 测评结果在不同列/行中展示。
- **语言隔离：** 英文（en）和中文（zh）分别报告，不得合并。
- **VQA 指标分层：** 论文 L2 平均（Full）、Lite 样本微平均（`xlrs.vqa.en.lite.micro_acc`）、Lite L3 宏平均（`xlrs.vqa.en.lite.macro_l3_acc`）分别保存。
- **Caption 主指标：** `xlrs.caption.en.bleu_4`、`xlrs.caption.zh.bleu_4`。
- **Grounding 主指标：** `xlrs.grounding.en.all.acc_0_5`、`xlrs.grounding.zh.all.acc_0_5`。
- **未公开 Full 任务：** 标注为"不可用"，不以 Lite 替代后冒充 Full。

### 5.4 MME-RealWorld-RS

- **正式测试范围：** Remote Sensing 域全量。**不得参与训练。**
- **Split 保护：** 无训练划分——该域全部样本不得用于训练。`doctor` 记录声明。
- **子任务：** Color、Count、Position。
- **主指标：** `mme_rs.acc.color`、`mme_rs.acc.count`、`mme_rs.acc.position`、`mme_rs.avg`（样本加权平均）、`mme_rs.avg_c`（类别等权平均）。
- **答案格式：** 期望输出为 A-E 五选一。无法解析为 A 至 E 的答案计为错误，并单列解析失败率。

### 5.5 通用训练隔离规则

所有四个数据集的训练隔离在 `doctor` 和 `run` 预检阶段自动检查。规则摘要：

- LEVIR-CC：train/val 可用，test 不可用于训练。
- VRSBench：train/val 可用，test 不可用于训练。
- XLRS-Bench：全量公开测试数据，禁止训练。
- MME-RealWorld-RS：Remote Sensing 域全量，禁止训练。


## 6. 首次生成测试清单和哈希

### 6.1 生成测试清单

首次配置好 `server.yaml` 后，运行以下命令验证配置和数据路径：

```bash
python -m m3rs_eval doctor --config configs/server.yaml
```

`doctor` 会：
1. 校验配置文件的必填字段和类型。
2. 检查所有数据路径、标注文件和图像文件是否存在且可读。
3. 扫描四数据集目录结构，确认 split 划分正确。
4. 检查被测系统命令是否可执行（兼容 PATH 解析，支持 Windows 和 Linux）。
5. 检查磁盘剩余空间是否超过配置阈值。
6. 检查 Python 依赖（PyYAML、jsonschema、psutil）和 GPU 工具（nvidia-smi，若适用）。
7. 验证指标注册表可加载且包含全部所需 `metric_id`。
8. 输出完整检查报告的 JSON，包含每个检查项的通过/失败/告警状态。

### 6.2 生成清单哈希

被测系统请求清单（所有请求行的有序集合）的 SHA-256 哈希在 `run` 命令执行时自动计算，并与 `run_manifest.json` 中的 `request_manifest_hash` 字段绑定。此哈希用于：
- 确保同一协议的运行请求完全一致。
- 判断两运行是否具有质量可比性。
- 恢复运行时校验请求内容未变化。

**操作者无需手动计算哈希。** 只需确保 `protocols/official_full_v1.yaml` 未被意外修改。


## 7. doctor、冒烟、全量和恢复命令

### 7.1 doctor（环境检查）

```bash
python -m m3rs_eval doctor --config configs/server.yaml
```

- 功能：检查配置、命令、数据路径、磁盘空间、Python 依赖、GPU 工具。
- 输出：JSON 格式的检查报告，每项含 `status`（pass/fail/warn）和 `message`。
- 退出码：0 表示全部必须项通过；非零表示正式评测所需条件不满足。**正式全量运行前必须 doctor 返回 0。**
- 参数：`--config`（必需）指定配置文件路径。

### 7.2 冒烟测试（smoke）

```bash
python -m m3rs_eval run --config configs/server.yaml --mode smoke --limit 2
```

- 功能：每个数据集任务只取前 N 条样本执行完整评测流程（请求生成、系统调用、预测校验、指标计算、资源采集、运行注册）。
- 参数：
  - `--config`（必需）：配置文件路径。
  - `--mode smoke`（必需）：指定冒烟模式。
  - `--limit N`（可选）：每个数据集任务取前 N 条样本。省略则使用协议默认的冒烟样本清单。
- 输出：`runs/<run_id>/` 完整运行包，但 `eligible_for_history=false`，不参与正式历史排名。
- 用途：快速验证系统连通性、JSONL 契约正确性和预测格式，确认无误后再执行全量运行。

### 7.3 全量测试（full）

```bash
python -m m3rs_eval run --config configs/server.yaml --mode full
```

- 功能：依次执行预检、请求生成、被测系统调用、预测校验、四数据集指标计算、资源汇总、运行注册、历史汇总和报告上下文生成。
- 参数：
  - `--config`（必需）：配置文件路径。
  - `--mode full`（必需）：指定全量模式。
- 输出：`runs/<run_id>/` 完整运行包，`eligible_for_history=true`（前提是状态为 `complete` 且协议检查通过）。
- 运行完成后，运行记录写入 `history/runs.csv`，指标写入 `history/metrics_long.csv`，覆盖数据写入 `history/coverage.csv`。

### 7.4 断点恢复（resume）

```bash
python -m m3rs_eval run --config configs/server.yaml --mode full --resume --run-id <RUN_ID>
```

- 功能：恢复一个未完成的运行（状态为 `incomplete` 或 `failed`）。
- 参数：
  - `--config`（必需）：**必须与原运行使用的配置完全一致**。
  - `--mode full`（必需）：恢复仅支持 `full` 模式。
  - `--resume`（必需）：开启恢复模式。**必须与 `--run-id` 同时使用。**
  - `--run-id <RUN_ID>`（必需）：要恢复的运行 ID。
- 恢复条件：请求清单哈希、系统版本、系统命令、配置哈希和协议哈希均与原运行一致时允许恢复。任一不匹配则拒绝恢复并报错。
- 恢复行为：
  - 已通过校验的预测复用原结果，跳过推理。
  - 缺失或失败的样本重新执行。
  - **恢复过程不得改变原 `run_id`。**
- 注意：`--resume` 和 `--run-id` 必须成对出现，单独使用任一个将报错。

## 9. 运行状态、错误码和失败样本处理

### 9.1 运行状态

Run ID 格式为 `YYYYMMDDTHHMMSS+0800__<system-version-slug>__<config-hash-8>`。

状态流转：

```text
created → preflight_passed → inference_running → evaluating
       → complete
       → incomplete
       → failed
```

- **`complete`：** 所有必需数据集、任务和主指标均完成，覆盖校验通过。可进入正式历史比较。
- **`incomplete`：** 进程正常结束但存在必需数据、预测或指标缺失。不可进入正式历史。
- **`failed`：** 预检、被测系统或评测程序异常终止。不可进入正式历史。
- 只有 `mode=full`、`status=complete` 且协议检查通过的运行才能进入正式历史比较（`eligible_for_history=true`）。

### 9.2 退出码（exit code）

| 退出码 | 含义 |
|--------|------|
| **0** | 成功：所有检查/评测正常完成 |
| **1** | 未知内部错误：非预期的异常（`Exception` 基类） |
| **2** | 配置/数据/协议/IO 错误：`ConfigError`、`ResumeMismatch`、`ValueError`、`OSError` |
| **3** | 预检或评测失败（doctor 检查不通过 / 运行状态非 complete） |
| **4** | 功能未实现：`rebuild-table` 或 `prepare-report` 尚未完成实现（过渡期占位） |

### 9.3 失败样本处理规则

所有失败类型**不得静默删除**，均计入 `n_failures` 并记录到 `failures.jsonl`：

| 失败类型 | 处理方式 | 对运行状态的影响 |
|----------|----------|------------------|
| 缺失预测 | 请求存在但预测文件中无对应 `sample_id` | 运行标记为 `incomplete` |
| 重复预测 | 同一 `sample_id` 出现多条预测行 | 全部计为失败，运行标记为 `incomplete` |
| 畸形预测 | JSON 解析失败或 Schema 校验不通过 | 全部计为失败，运行标记为 `incomplete` |
| 未知 sample_id | 预测中出现了请求清单中没有的 `sample_id` | 该预测丢弃并计为失败 |
| status=error | 被测系统主动报告错误 | 计为失败，继续处理后续样本 |
| 非零退出 | 被测系统命令返回非零退出码 | 运行标记为 `failed`，保留已生成的预测 |
| 超时 | 被测系统命令超过 `timeout_seconds` | 运行标记为 `failed`，保留已生成的预测 |

### 9.4 预测校验流程

评测器按以下顺序校验预测文件：

1. 读取预测 JSONL，检查每行是否为合法 JSON。（非法行 → 畸形）
2. Schema 校验：每行是否满足 `prediction.schema.json`。（不满足 → 畸形）
3. `sample_id` 去重检查。（重复 → failure）
4. 与请求清单交叉比对：每个请求 `sample_id` 是否有对应预测行。（缺失 → failure）
5. 检查预测行中是否有请求清单未包含的 `sample_id`。（未知 ID → failure）
6. status=ok 的行检查 `prediction` 或 `boxes` 是否有效。（无效 → 按畸形处理）
7. status=error 的行记录 `error_code` 和 `error`。

### 9.5 错误码在预测中的使用

被测系统在预测行中使用以下错误码报告失败：

| error_code | 含义 |
|------------|------|
| `timeout` | 单样本推理超时 |
| `inference_error` | 模型推理错误（OOM、CUDA error 等） |
| `parse_error` | 模型输出解析失败 |
| `cancelled` | 推理被中断 |
| `unknown` | 未分类错误 |

这些错误码在 `failures.jsonl` 中汇总，按数据集和任务分组统计。


## 10. 更新核心《评测表》的步骤

### 10.1 重建工作簿

当历史数据（`history/runs.csv`、`metrics_long.csv`、`coverage.csv`）更新后，运行以下命令从历史结构化数据重建 `评测表.xlsx`：

```bash
python -m m3rs_eval rebuild-table
```

**重要说明：**
- `rebuild-table` 从历史 CSV/JSONL 重建工作簿，不直接读取或相信工作簿中已有的手工数值。这确保 Excel 始终是历史数据的忠实展示。
- `rebuild-table` 内部调用 `tools/build_workbook.py`（Python 脚本），需要 Node.js 18+ 环境。
- 工作簿包含八个工作表：`使用说明`、`核心评测表`、`指标长表`、`运行元数据`、`数据覆盖`、`对比看板`、`指标字典`、`协议与质检`。
- 工作簿中的公式（如改善率计算、条件格式）由 `build_workbook.py` 自动生成。

### 10.2 验证工作簿

重建完成后，检查以下项目：

1. `核心评测表` 的行数与 `runs.csv` 中 `eligible_for_history=true` 的运行数一致。
2. `指标长表` 中的每个 `metric_id` 都能在 `指标字典` 工作表中找到。
3. 工作簿中无 `#REF!`、`#VALUE!`、`#DIV/0!` 等公式错误。
4. 表头、单位、筛选器、冻结窗格和条件格式正确应用。
5. 缺失值显示为空白或"N/A"，不以"0"替代。

### 10.3 手动注意事项

- 不要在 Excel 中手动修改指标数值。如需修正，应修改原始运行数据并重新 `rebuild-table`。
- 可在 `核心评测表` 的 `备注` 列添加人工注释，但不要覆盖公式单元格。
- `指标字典` 工作表内容在 `rebuild-table` 时从 `registry/metrics.yaml` 自动同步。


## 11. 生成报告上下文并使用提示词的步骤

### 11.1 生成报告上下文

对指定的运行（或最新的兼容运行），生成结构化报告上下文 JSON：

```bash
# 为指定的运行生成上下文
python -m m3rs_eval prepare-report --run-id <RUN_ID>

# 为最新的兼容正式运行生成上下文
python -m m3rs_eval prepare-report --latest-compatible
```

- 两个参数互斥（`--run-id` 和 `--latest-compatible` 二选一，不可同时使用）。
- `--run-id <RUN_ID>`：指定目标运行 ID。
- `--latest-compatible`：自动选择最新的兼容正式运行作为目标。

`prepare-report` 输出一个 JSON 文件（`reports/report_context_<run_id>.json`），包含：
- `current_run`：目标运行的完整信息及全部指标
- `baseline_run`：最近兼容正式运行（若存在）
- `all_compatible_runs[]`：全部历史兼容正式运行列表
- `historical_best`：每个 metric_id 的历史最佳值
- `dataset_sections[]`：按四数据集分组的指标
- `resource_metrics`：资源指标对比
- `failures`：失败样本分类
- `comparability`：可比性判定
- `incompatible_runs[]`：不可比运行及原因
- `protocol_diff`：协议差异

### 11.2 使用 LLM 生成评测对比报告

1. 将 `reports/report_context_<run_id>.json` 的完整内容作为上下文提供给 LLM。
2. 使用 `prompts/生成评测对比报告提示词.md` 作为系统提示词或用户提示词。
3. LLM 将生成固定十节的 Markdown 对比报告。

### 11.3 报告内容要求（摘自设计 §18）

提示词确保：
- 所有数据来自报告上下文，**不得编造**。
- 每个结论引用 `run_id` 和 `metric_id`。
- 缺失值、不可比值和不确定结论明确说明。
- 原因分析标记为假设（`【假设】`），并给出验证实验。
- 输出有效 Markdown，无前言后语。
